# Sistema de Internacionalização (i18n) en-US / pt-BR Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Implement full internationalization across ApiDot with `en-US` as canonical default and `pt-BR` as selectable option, including user preference persistence in backend (`User.Locale`), SSO claim extraction (`locale`), local client caching, language selector UI, and migration of all user-facing interface text.

**Architecture:** Type-safe dictionary-based i18n system driven by a lightweight Zustand store (`useI18nStore`) and custom hook (`useTranslation`), persisted to `localStorage` for instant client hydration and synchronized with `ApiDot.Server` via `PATCH /api/auth/me/locale`. Backend extends `User` with nullable `Locale` column, maps standard OIDC `locale` claim on JIT provisioning, and exposes user locale in `AuthUserDto`.

**Tech Stack:** Next.js 15 (App Router), React 19, TypeScript, Zustand, Tailwind CSS, .NET 9 (C# 13), EF Core (SQLite / PostgreSQL), Minimal APIs, Vitest, xUnit, FluentAssertions.

**Spec:** `docs/plans/2026-10-30-i18n-system-design.md`

---

## Global Constraints

- Default language must be strictly `en-US` for all unauthenticated/new visitors without sniffer-induced SSR hydration mismatches.
- Dictionaries in `src/i18n/locales/` (`en-US.ts` and `pt-BR.ts`) must adhere to strict type checking: TypeScript must error if any key in `en-US` is missing or typed differently in `pt-BR`.
- Zero new runtime NPM dependencies: no `next-intl`, no `i18next`, avoiding bundle bloat and wrapper overhead in Vitest tests.
- Backend `User.Locale` must be nullable `string?` with max length 16: `null` represents unconfigured preference so initial SSO login can set it; explicit user change sets it permanently and is never overwritten by subsequent SSO logins.
- All 825+ frontend Vitest tests and 513+ backend .NET tests must pass with zero regressions.

---

## Review Focus

1. **Missing Translation Key Fallback**: When a key exists in `en-US` but is undefined in `pt-BR`, translator returns the `en-US` string instead of empty string or crashing.
2. **SSO Overwrite Prevention**: If a user previously set `Locale = "en-US"` explicitly, a subsequent SSO login with Authentik sending `locale: "pt-BR"` must NOT overwrite the user's explicit choice.
3. **Invalid Locale Protection**: `PATCH /api/auth/me/locale` with invalid values (e.g., `"fr-FR"`, `"unknown"`, injection strings) must return `400 Bad Request` with `ProblemDetails`.
4. **Parameter Interpolation Safety**: `t('common.count', { count: 0 })` must correctly format falsy values (e.g. `0`, `false`) and ignore missing parameters without throwing.
5. **Hydration Determinism**: First render on server and client must evaluate to `en-US` when `localStorage` is empty, avoiding React 19 hydration mismatch warnings.

```csharp
group.MapPatch("/me/locale", async (
    UpdateLocaleRequest? request,
    ICurrentUserContext userContext,
    IAuthService authService,
    CancellationToken ct) =>
{
    if (!userContext.UserId.HasValue) return Results.Unauthorized();
    if (request == null || string.IsNullOrWhiteSpace(request.Locale))
        return Results.BadRequest(new { message = "Locale is required." });

    var validLocales = new[] { "en-US", "pt-BR" };
    if (!validLocales.Contains(request.Locale, StringComparer.OrdinalIgnoreCase))
        return Results.BadRequest(new { message = "Supported locales are: en-US, pt-BR." });

    var success = await authService.UpdateUserLocaleAsync(userContext.UserId.Value, request.Locale, ct);
    if (!success) return Results.NotFound();
    return Results.NoContent();
});
```
Update root fallback in `GET /api/auth/me`: `new AuthUserDto(Guid.Empty, "root@local", "Root (Dev/Test)", true, "en-US", [])`.
